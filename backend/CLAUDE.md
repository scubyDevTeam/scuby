|---|---|

## Java version

One version, three places that must agree — change them in one commit:

1. `pom.xml` `<java.version>` — compilation, and Jib's base image `eclipse-temurin:${java.version}-jre@sha256:…`.
2. `.java-version` — jenv locally; CI reads it (`java-version-file` in `.github/workflows/backend.yml`).
3. The Jib base-image digest in `pom.xml` — look it up with `docker buildx imagetools inspect eclipse-temurin:<version>-jre` (the top-level index `Digest:`, whose manifests list linux/amd64 and linux/arm64), verify it with `docker buildx imagetools inspect eclipse-temurin:<version>-jre@<digest>`; never copy a digest from a plan or a chat.

The Maven enforcer fails `validate` on any JDK outside `[25,26)` or Maven older than 3.9.

## Package rules

- Enforced by ArchUnit (the build fails): package by feature, **flat**: `platform` (domain-free), foundations `identity`, `uploads`, `pets`,
  verticals `cases` (later `adoption`, `help`…). No layer subpackages.
  Foundations today: identity (accounts, sessions, phone), uploads (slots, media store), pets (pet + responsibility). Vertical: cases (lost cases, sightings, feed, the caller's cases).
- Package-private by default. A class another feature uses is `public` **and** `@ModuleApi`.
- Dependencies: `platform` → nothing of ours; foundations → `platform` only; verticals →
  foundations + `platform`, never another vertical. A new feature package is added to
  `ArchitectureRules.FOUNDATIONS` or `VERTICALS` in the same commit.
- Roles (ArchUnit): `@ApiComponent` and `@WorkerComponent` never depend on each other; every `@RestController` is an `@ApiComponent`; every `@Scheduled`/`@SqsListener` method is in a `@WorkerComponent`.
- **Enforced by review only** (nothing fails the build): each table has **one writing feature** (reads may join any table; `db.generated` is shared), and cross-feature side effects go through the outbox, never a direct call to another vertical.

## Writing an endpoint

1. Request/response records by hand, matching the contract (snake_case comes from Jackson).
   Responses are complete: every field present, `null` not absent.
2. Controller (`@ApiComponent @RestController`, package-private) takes `Caller` (who asks: person?,
   device, IP hash) and/or `Account` (sign-in required) parameters. A `session` endpoint is also
   declared in the feature's `SecurityRules` bean.
3. Service methods own transactions. Never a transaction across a request; never `@Transactional`
   on a controller or filter.
4. jOOQ for every query. Time comes from the `Clock` bean, passed as a parameter — never `now()`
   in SQL, never `Instant.now()`.
5. Viewer-dependent responses: **access → facts → derivation → record**. Load `*Facts` according
   to the access (private facts are not even queried for the public); `XDerivation.derive(facts,
   viewer, now, …)` is pure (no Spring, jOOQ, I/O, clock or randomness) and table-tested in
   `XDerivationTest` (PIT mutates it; ≥ 80 %).
6. Errors: throw `ApiException(ErrorCode…, message, fields, details)`; fields are wire paths.
7. Never call S3 (`PhotoAttachments`, `MediaStore.isStored`) inside a transaction: check photos first, then open a `TransactionTemplate` for the writes.
8. A required request field that can be `null` is `@JsonProperty(required = true)`, so absence is `validation_failed`; length checks that mirror a DB `CHECK` use `@CodePoints`, not `@Size` ([backend.md](../docs/eng/backend.md) · Code structure, Request validation).
9. A pet is created only through `Pets.createOwned` inside the caller's transaction; someone else's pet is `not_found` via `Pets.requireOwnedBy`, never `forbidden`.
10. Every photo URL in a request body goes through `PhotoAttachments.requireAttachable(urls, purpose, caller, wireField)`.
11. **Lock order:** `person` first (`People.lock`, `FOR NO KEY UPDATE`), then advisory locks, then the rest; a path that locks a person and then a case follows it and gets a race test against «Lo vi» ([backend.md](../docs/eng/backend.md) · Lock order).

## Tests

- Endpoint tests are `@IntegrationTest`, call `testDb.reset()` first, and go through `ApiClient`:
  every response is validated against `openapi.json` and the request's SQL statements are counted
  against `StatementCeilings` (add your endpoint's line; a ceiling never grows with row counts —
  seed several rows to prove it).
- A contract route is called through the checked methods; `raw()` refuses a documented path, and `unchecked(…, reason)` is the escape (for a status the contract does not list, such as the Origin `403`). A controller route missing from `openapi.json` fails `ContractCoverageTest`.
- Viewer-dependent endpoints get a **leak test**: as a non-owner, every owner-only field is `null`.
- Time travel: `MutableClock` (`advance`, `set`). Codes sent by email/SMS: `RecordingEmailSender`,
  `RecordingSmsSender`. Signed-in shortcut: an injected `Accounts` bean's `signIn(api, email)` (sets the `__Host-session`
  cookie).
- Connection hygiene: `ConnectionSampler` samples the pool while the controller starts, and
  `StatementRecorder.autoCommits()` says which statements ran outside a transaction.
- A deployed profile's required setting goes into `ProfileStartupTest.REQUIRED` (dummy value): the
  test proves `staging` and `prod` start with them and refuse to start without each. A deployed
  profile combined with `local` or `test` is still deployed; keys must be non-blank, at least 32
  characters and not the shipped default.
- A new writable table goes into `TestDb.MUTABLE_TABLES` (or `TestDb.REFERENCE_TABLES` for seeded reference data); `HarnessSelfTest` fails for a table in neither.

## Migrations and indexes

- Flyway file names are timestamps: `V20261029_1430__what.sql` (never sequence numbers) — **on
  every branch**, enforced by `MigrationNamesTest`. `spring.flyway.out-of-order` is on, so a migration
  from a branch that merges later still runs; therefore a migration must not depend on another
  branch's migrations (decision #44). Each starts with a comment: what it is for, which doc owns it. Qualify
  tables with `scuby.` inside PL/pgSQL.
- **Two kinds of index, justified differently.**
  - *Integrity* (a PK, a UNIQUE, a partial unique that enforces a rule or settles a race): justified
    by the rule it protects. Table size is irrelevant.
  - *Performance:* justified only by growth. Before adding one, answer in the migration comment:
    1. **Can the table grow without bound?** Rows never deleted (cases, sightings) — yes. Rows a
       purge keeps to a window (code sends at 30 days) — bounded. Reference data — no.
    2. **How often does the query run?** Per page view, per write, or rarely.
    3. **What happens without the index** once the table has grown? A full scan on the hot path,
       or a few milliseconds on a rare one.

    A seeded plan check shows only that the index *would be used*. Seeding thousands of rows always
    makes a sequential scan lose, so a passing check is not the justification. Prefer bounding the
    table (a purge) over indexing it. A small, bounded or rarely-read table gets no performance
    index.
  - When an index is justified: write the failing plan check first (`PlanAssert`), then the index.
    Its migration comment carries the growth answer, the query, the plan before/after, the write
    cost and overlaps. Every new index, of either kind, is listed for human approval in the task
    report (review-enforced).
- A predicate a partial index depends on (`status = 'active'`) is a literal in jOOQ — `DSL.inline("active")` — never a bind value ([backend.md](../docs/eng/backend.md) · Migrations and indexes).

## What reviewers check (humans)

Derivation test tables (the business rules), access policies (who sees whose phone and location),
migrations (data changes are not undone by a revert), jOOQ queries (indexes, PostGIS), anything
exposing personal data. Automation covers shape, architecture and test strength.
